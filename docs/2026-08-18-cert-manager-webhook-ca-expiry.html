Cert-Manager Webhook CA Expiry — Cluster-Wide TLS Renewal Failure

📊 Executive Summary

On August 18, 2026, the Orion staging UI's "View Logs" feature returned Failed 0 for all clients. Investigation revealed that the KubeBridge API at k8sapi.fetchitdata.cloud was unreachable due to an expired TLS certificate.

The TLS cert (Let's Encrypt, 90-day lifetime) had expired earlier that day at 05:42 UTC. It should have been auto-renewed by cert-manager on July 19, but cert-manager's own internal webhook CA certificate had expired on July 3 — silently breaking all certificate operations cluster-wide for 46 days. No renewals, no issuances, no error alerts.

The fix required deleting the expired webhook CA secret and restarting all cert-manager components. Once the webhook was healthy, cert-manager immediately processed pending renewals for 5 certificates that had been blocked. All certificates across the cluster are now valid and READY.

🔴 Symptom & Detection

The incident was detected when the Orion UI's "View Logs" button (which calls GET /api/Logs/GetPodLogs?internalIdentifier=...) returned Failed 0 for all clients on the staging environment.

User-Visible Symptom
GET https://orion-staging.fetchitdata.cloud/api/Logs/GetPodLogs?internalIdentifier=cityvetoaklawn

Response: "Failed 0"

Why "Failed 0"?

The GetPodLogs endpoint calls KubeBridge.GetPodLogsAsync(), which uses RestSharp to call https://k8sapi.fetchitdata.cloud/phone-worker/{id}. When RestSharp cannot establish a TCP/TLS connection at all, it returns StatusCode = 0 (not an HTTP status — a transport-level failure). The code returns this as $"Failed: {response.StatusCode}", which renders as Failed 0. 

// KubeBridge.cs — GetPodLogsAsync()
if (!response.IsSuccessful || string.IsNullOrWhiteSpace(response.Content))
{
    return $"Failed: {response.StatusCode}";  // StatusCode = 0 → "Failed 0"
}

The underlying TLS error was: SEC_E_CERT_EXPIRED (0x80090328) — The received certificate has expired.

🔍 Root Cause Analysis

Primary: Cert-Manager Webhook CA Expiry

cert-manager uses a Kubernetes ValidatingWebhookConfiguration to validate all CertificateRequest resources before they are persisted. This webhook runs as its own deployment (cert-manager-webhook) and serves HTTPS using a self-signed CA stored in the secret cert-manager-webhook-ca in the cert-manager namespace.

This CA has a 1-year fixed lifetime and does not auto-rotate in the installed version. When it expired on July 3, 2026, the Kubernetes API server could no longer verify the webhook's TLS certificate when calling it for validation. Every CertificateRequest creation was rejected with an internal webhook TLS error.

The Failure Chain
cert-manager-webhook-ca secret expires (Jul 3, 1-year self-signed CA)
    ↓
Kubernetes API rejects all webhook calls (x509: certificate has expired)
    ↓
All CertificateRequest creations fail silently (re-queued indefinitely)
    ↓
No Let's Encrypt renewals succeed cluster-wide for 46 days
    ↓
k8sapi.fetchitdata.cloud TLS cert expires (Aug 18, first to hit 90-day limit)
    ↓
RestSharp returns StatusCode=0 (TLS handshake failure)
    ↓
Orion displays "Failed 0" for pod log requests

Why Was This Silent for 46 Days?

  • cert-manager controller logged the webhook error but no alerting was configured on cert-manager logs or Certificate Ready state
  • The Certificate resources continued showing READY = True with stale status (the condition was not updated until the secret was deleted)
  • All existing certificates remained valid during the 46-day window — the failure only became visible when the first cert actually expired
  • The k8sapi endpoint is only called from the Orion UI's "View Logs" feature, which is used infrequently

The broker cert's previous renewal was 90 days old and its renewal had been blocked — it was effectively days away from expiry.

✔ Fix Applied

Step 1 — Delete Expired Webhook CA Secret

kubectl delete secret cert-manager-webhook-ca -n cert-manager

Step 2 — Restart All Cert-Manager Components

kubectl rollout restart deployment cert-manager -n cert-manager
kubectl rollout restart deployment cert-manager-cainjector -n cert-manager
kubectl rollout restart deployment cert-manager-webhook -n cert-manager

On restart, the cainjector regenerated a fresh self-signed CA (valid through 2027-08-18), the webhook signed a new serving certificate from it, and the controller immediately began processing all queued certificate renewals.

📝 Lessons Learned

Silent Infrastructure Failures Are the Most Dangerous

This failure was completely invisible for 46 days. cert-manager's Certificate resources continued reporting READY = True with stale status, and the webhook error was only visible in controller pod logs. The first user-visible symptom appeared only when a certificate actually expired — by which point 5 certificates were overdue for renewal and the cluster was days away from cascading outages across broker, orion, and cleartext.

Cert-Manager's Webhook CA Is a Single Point of Failure

A single expired self-signed CA secret — which is not managed by cert-manager itself and has no auto-rotation in the installed version — disabled all certificate operations across the entire cluster. This is a known issue in older cert-manager versions. Upgrading to a version with automatic CA rotation (or adding a CronJob to proactively rotate it) would eliminate this class of failure.

RestSharp StatusCode 0 = Transport Failure

A RestSharp StatusCode of 0 is not an HTTP status code — it means the request never completed (DNS failure, connection refused, or TLS error). Application code that surfaces this to users should distinguish transport errors from HTTP errors and provide meaningful diagnostics rather than raw numeric codes.
