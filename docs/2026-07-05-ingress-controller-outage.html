📊 Executive Summary

On July 5, 2026, all production services routed through the nginx ingress controller became completely unreachable. The cluster nodes and pods were healthy and connectable via Headlamp, but all external HTTP/HTTPS traffic was silently dropped.

The root cause was a complete absence of running ingress controller pods. All replicas were either in Evicted or ImagePullBackOff state. This was a continuation of an image pull issue first identified in the July 2, 2026 incident, where the original image from marketplace.azurecr.io became unpullable. A prior remediation attempt had updated the image to registry.bitnami.com, which is not resolvable from cluster nodes — leaving every new pod unable to pull.

The incident was resolved by switching to the functionally equivalent official image from registry.k8s.io/ingress-nginx/controller:v1.1.1 and correcting the pod security context to match what the official image requires.

🔍 Root Cause Analysis

Primary: Ingress Image Chain Failure

The outage was a continuation of the July 2 incident. The ingress controller deployment had been configured with a Bitnami-distributed image from Azure Marketplace that became unpullable. A prior fix attempt changed the registry to registry.bitnami.com, which cluster nodes cannot resolve via DNS. As old pods were evicted over time, new replacement pods could not start, reducing the running replica count to zero.

The Failure Chain
marketplace.azurecr.io/bitnami/nginx-ingress-controller:1.1.1  (lapsed credentials)
        ↓ remediation attempt
registry.bitnami.com/bitnami/nginx-ingress-controller:1.1.1    (DNS: NXDOMAIN from nodes)
        ↓ all new pods ImagePullBackOff
        ↓ all old evicted pods non-recoverable
        ↓ 0/2 replicas running
        ↓ LoadBalancer has no endpoints
        ↓ ALL ingress routes return connection refused

Secondary: Security Context Mismatch on Image Swap

When the image was correctly changed to registry.k8s.io/ingress-nginx/controller:v1.1.1, the pod still crashed immediately due to the security context carried over from the original Bitnami deployment. Bitnami images run as UID 1001; the official ingress-nginx image expects UID 101. With fsGroup: 1001 applied, the container could not write the SSL certificate file required during startup initialization. 

F0705 23:17:39.511773  7  ssl.go:388
unexpected error storing fake SSL Cert:
could not create PEM certificate file /etc/ingress-controller/ssl/default-fake-certificate.pem:
open /etc/ingress-controller/ssl/default-fake-certificate.pem: permission denied

Tertiary: RingCentral NullReferenceException (Concurrent)

A concurrent but independent issue was identified: MQTT broker connectivity loss (connection refused on broker.fetchitdata.cloud:443) triggered rapid reconnect loops in phone-worker pods, and when the RingCentral WebSocket error handler received a WSG-903 Absolute timeout response, the null errorCode field in the error body caused a NullReferenceException — crashing affected pods.

This secondary issue was also resolved: the MQTT broker became reachable again once the ingress controller was restored (broker.fetchitdata.cloud routes through ingress), and the code-level null-reference was patched in PhoneSystemsPlugins/RingCentral/PhoneSystem.cs.

✅ Fixes Applied

Fix 1 — Ingress Controller Image (Critical)

Switched from the unreachable Bitnami registry to the official upstream ingress-nginx image on registry.k8s.io, which resolves correctly from all cluster nodes. The entrypoint (/nginx-ingress-controller) and all command-line args are identical between both distributions at v1.1.1.

Before
registry.bitnami.com/bitnami/nginx-ingress-controller:1.1.1-debian-10-r0
After
registry.k8s.io/ingress-nginx/controller:v1.1.1

Fix 2 — Pod Security Context (Critical)

Corrected the security context to match the official ingress-nginx image's expected UID/GID, removing the Bitnami-inherited fsGroup: 1001 and setting the correct runAsUser: 101 with NET_BIND_SERVICE capability required to bind ports 80 and 443.

Before (Bitnami-inherited)
spec:
  template:
    spec:
      securityContext:
        fsGroup: 1001
      containers:
        - securityContext:
            allowPrivilegeEscalation: true
After (official image)
spec:
  template:
    spec:
      securityContext:
        runAsUser: 101
        runAsGroup: 101
      containers:
        - securityContext:
            allowPrivilegeEscalation: true
            runAsUser: 101
            capabilities:
              add: ["NET_BIND_SERVICE"]

Fix 3 — RingCentral NullReferenceException (Code Patch)

Applied null-safe navigation operators in WsExtension_MessageReceived to prevent crashes when a RingCentral WebSocket error response contains a null errorCode or recoveryState field. The null-forgiving operator (!) in the original code bypassed compiler safety checks and caused a runtime crash.

Before — PhoneSystem.cs:165
// Crashes if errorCode is null
if (!reconnecting
    && wsgMessage.meta.type == MessageType.Error
    && (wsgMessage.body.errorCode as string)!.StartsWith("OAU-"))

// Crashes if recoveryState is null
if ((wsgMessage.body.recoveryState as string) != "Successful")
After — PhoneSystem.cs:165
// Null-safe: evaluates to false if errorCode is null
if (!reconnecting
    && wsgMessage.meta.type == MessageType.Error
    && (wsgMessage.body?.errorCode as string)?.StartsWith("OAU-") == true)

// Null-safe: evaluates to != "Successful" if recoveryState is null
if ((wsgMessage.body?.recoveryState as string) != "Successful")

📝 Lessons Learned

Remediation Validation

The prior fix on July 2 changed the image registry without validating that the new registry was reachable from cluster nodes. DNS resolution for external registries should always be tested from within the cluster (kubectl run dns-test --image=busybox ...) before applying an image change, especially for critical infrastructure components.

Cascading Infrastructure Failures

The ingress controller outage broke MQTT connectivity (broker.fetchitdata.cloud), which in turn triggered a code-level crash in phone-worker pods. Infrastructure dependencies must be considered when assessing blast radius — a single broken deployment caused both total external traffic loss AND application-level pod crashes across 5 client namespaces.

Image Registry Strategy

The cluster should maintain a private ACR mirror for critical infrastructure images (ingress controller, cert-manager, etc.) to avoid dependency on third-party registries and marketplace credentials. The private ACR (obrienvet-fxh5ecewbmcjbjc4.azurecr.io) already exists in the environment and should be used as a pull-through cache.
