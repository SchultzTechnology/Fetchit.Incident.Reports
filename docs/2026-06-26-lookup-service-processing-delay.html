Root cause analysis and resolution of MQTT message processing backlog

📊 Executive Summary

During a routine log review, incoming call messages were observed being processed by the staging environment up to 2.5 minutes before the production environment. Investigation revealed this was not a routing issue but a serial message processing bottleneck in the MQTT client — messages were queuing behind one another rather than being processed concurrently. The fix was deployed same-day to both staging and production.

🏗️ Architecture Context

The Lookup Service subscribes to MQTT topics published by PhoneSystem integrations. The two environments use different subscription strategies:

Environment MQTT IncomingTopic Replicas Subscription Type
Staging lookupservice/calls/incoming 1 Regular — receives every message
Production $share/lookupgroup/lookupservice/calls/incoming 3 Shared group — each message delivered to one replica

Staging intentionally subscribes to the same underlying topic as production, acting as a live canary — receiving the same real traffic to validate code changes before they are tagged for production release. This is by design.

The shared subscription ($share/lookupgroup/...) on production ensures the message load is distributed across the 3 replicas rather than tripling the work. This is also correct behaviour.

🐛 Root Cause

Despite HandleMessageReceived being declared async Task, the MQTTnet managed client invokes the handler sequentially — it awaits each call to completion before dispatching the next message. This means each production replica could only process one message at a time, despite having async I/O internally.

Compound factors made this worse in production specifically:

  • 3 replicas with a shared subscription means each replica processes its share of the total load, not a third of it — each one was still serially queueing.
  • Slow PMS API calls (e.g. Digitail GetClinicId failures, DaysSmart token refreshes) could block an entire replica's queue for seconds at a time.
  • A _startTime vs processed timestamp delta of ~2.5 minutes was observed in logs, confirming queue accumulation.
Confirmed in logs — 14:26:17

[ERR] schultztechnologydigitail: Failed to get clinic ID. Status: 0
[ERR] Error occurred in MQQTClient - HandleMessageReceived method.
System.Exception: Failed to retrieve clinic data.

A single failing Digitail call was holding up the queue for that entire replica, causing every subsequent message to wait behind it.

✅ Fix

The solution decouples message acknowledgement from message processing. HandleMessageReceived now returns Task.CompletedTask immediately after firing the processing work onto the thread pool. The MQTT client can then dequeue and dispatch the next message without waiting. 

// BEFORE — blocks the MQTT dispatcher until fully processed
private async Task HandleMessageReceived(MqttApplicationMessageReceivedEventArgs eventArgs)
{
    // ... all processing inline, next message waits here
}

// AFTER — returns immediately, processing runs concurrently
private Task HandleMessageReceived(MqttApplicationMessageReceivedEventArgs eventArgs)
{
    eventArgs.AutoAcknowledge = false;              // manual ACK after processing
    _ = Task.Run(() => ProcessMessageAsync(eventArgs));  // fire and continue
    return Task.CompletedTask;                        // dispatcher is free immediately
}

private async Task ProcessMessageAsync(MqttApplicationMessageReceivedEventArgs eventArgs)
{
    try
    {
        // ... all DB + PMS API work runs here, concurrently with other messages
    }
    finally
    {
        await eventArgs.AcknowledgeAsync(CancellationToken.None);  // ACK only after completion
    }
}

Manual acknowledgement (AutoAcknowledge = false) ensures that even if processing fails, the message is still acknowledged — preventing undeliverable messages from re-queuing infinitely. Errors are caught, logged to Sentry, and the message is released.

📋 Additional Findings

TLS Certificate Expired

The TLS certificate on signoz.fetchitdata.cloud has expired (SEC_E_CERT_EXPIRED). Browser and curl access require bypassing certificate validation. This should be renewed.

Recurring Digitail GetClinicId Failures

Client schultztechnologydigitail is consistently failing with Status: 0 on GetClinicId(). Under the old serial model, each failure contributed to queue backlog. Under the new concurrent model the impact is contained, but the underlying Digitail API issue should be investigated.

Kubernetes ConfigMaps Out of Sync

Prior to this session, both the staging and production ConfigMaps were missing No Reset On Close=true;Minimum Pool Size=0 on the NeonOrionContext connection string. This was corrected in the local config files and will be applied automatically by the updated CI pipeline on next deploy.

CI Pipeline Now Applies Kubernetes Configurations

The CI workflows (dotnet-ci.yml and tagged-ci.yml) were updated to run kubectl apply -f Kubernetes.Configurations/[env]/ before restarting deployments, and now use kubectl rollout restart instead of manual scale-to-zero cycling.
