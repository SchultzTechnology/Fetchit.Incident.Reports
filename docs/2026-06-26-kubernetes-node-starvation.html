⚠️ Infrastructure Incident

AKS Node Starvation — Kubelet Eviction Event

Resource exhaustion on aks-npapps2-34924295-vmss000006 causing TaintManagerEviction and pod disruption

Date June 26, 2026
Node aks-npapps2-34924295-vmss000006
VM Size Standard_E2bds_v5 (2 vCPU)
Status ⚠ Self-Recovered · Action Required

📊 Executive Summary

At approximately 15:10 UTC, a Kubernetes node running 102 pods on a 2-core VM reached CPU saturation. The kubelet — the node's management process — was starved of CPU cycles and failed to send its heartbeat to the Kubernetes control plane. The cluster declared the node NotReady and initiated a TaintManagerEviction.

The node self-recovered when the eviction process reduced pod network activity, relieving CPU pressure enough for the kubelet to resume heartbeating. No data was lost, but the event exposed a serious infrastructure risk: the node is critically over-tenanted and will fail again under load.

🐛 Root Cause Analysis

This was not a software bug. It was a Resource Exhaustion event — 102 pods fighting over 2 CPUs, with the node's management system losing the fight.

Contributing Factor 1 — Extreme Pod Density

102 / 110 pods on a 2-core VM

A Standard_E2bds_v5 has 2 vCPUs. Managing liveness/readiness probes, metric scraping, and log rotation for 102 separate containers is an enormous overhead on a 2-core machine. The kubelet itself competes with every other process for those same 2 cores.

Contributing Factor 2 — 273% CPU Limit Overcommitment

CPU Limits: 5200m on a 1900m node

Pod requests (1356m, 71%) were reasonable — the scheduler used them to place pods. But limits (5200m, 273%) allow pods to burst well beyond what physically exists. When several pods burst simultaneously:

  • The Linux kernel's CFS scheduler begins aggressively throttling all processes
  • The kubelet gets throttled along with everything else
  • It can no longer complete its heartbeat within the 40-second window

The Cascade

StepWhat happenedEffect
1 Pod burst activity spikes CPU All processes throttled by kernel
2 Kubelet misses 40s heartbeat Control plane marks node NotReady
3 TaintManagerEviction starts Pods begin to be terminated/suspended
4 Network traffic reduced by eviction CPU pressure drops, kubelet recovers
5 Kubelet sends heartbeat Node returns to Ready, eviction cancelled

🛠️ Recommended Actions

This node will fail again under similar load conditions without structural changes. The following actions are recommended in priority order:

🔴 Priority 1 — Upgrade the Node Pool VM Size

Move the npapps2 node pool from Standard_E2bds_v5 (2 vCPU) to at least a Standard_E4bds_v5 (4 vCPU) or Standard_E8bds_v5 (8 vCPU). This gives the kubelet dedicated breathing room and reduces the proportion of CPU consumed by node management overhead.

Impact: Eliminates the kubelet starvation failure mode entirely.

🟠 Priority 2 — Reduce Max Pods Per Node

Lower --max-pods on this node pool (currently 110) to force Kubernetes to spread pods across more nodes rather than packing them onto one. A value of 50–60 is more appropriate for a 2-core node.

Impact: Reduces pod density per node, lowering management overhead on the kubelet.

🟠 Priority 3 — Lower CPU Limits on phone-worker Pods

The 273% overcommitment is the trigger. Set CPU limits on phone-worker pods to a value closer to their actual usage rather than allowing unbounded bursting. A limit of 200m–500m per pod would prevent a burst storm from saturating the node.

Impact: Prevents simultaneous bursting from triggering kernel-level throttling of the kubelet.

🔵 Priority 4 — Add Node Autoscaling

Enable the AKS Cluster Autoscaler on this node pool so that when pod demand increases, new nodes are provisioned automatically rather than all load concentrating on a single node.

Impact: Prevents this class of problem from recurring as the number of phone-worker clients grows.

✅ What Went Well

  • The cluster self-recovered without manual intervention.
  • The TaintManagerEviction mechanism worked as designed — by reducing load it inadvertently resolved the very condition that triggered it.
  • No persistent data was lost. Application services resumed normally after recovery.
  • SigNoz log retention allowed full post-hoc reconstruction of the event timeline.
