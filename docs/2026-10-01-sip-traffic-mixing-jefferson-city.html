📊 Executive Summary

On October 1, 2026, between 08:42 and 13:57 UTC, the phone-worker pod for Jefferson City Animal Hospital (jeffersoncityanimalhospital namespace) received SIP traffic addressed to two different identities simultaneously:

  • sip100u_stsdino — the correct, actively registered SIP account for this client
  • sip101u_stslakepine — a different client's SIP account, misdirected to this pod

Both streams were processed by the same pod (phone-worker-679c475bb9-td45p). The phone-worker application accepted and processed inbound INVITEs (calls) from both identities without distinguishing them, meaning at least 3 real phone calls intended for the stslakepine client were processed as if they belonged to Jefferson City.

The mixing stopped at 13:57 UTC when the pod was replaced during a rolling update. The new pod received only stsdino traffic. The root cause is a SIP registrar-side stale Contact binding combined with AKS node NAT port recycling.

🔍 Root Cause Analysis

How SIP Authentication Works (and Doesn't)

SIP authentication is unidirectional. When a phone-worker pod sends a REGISTER request to the SIP registrar, it authenticates with a username and password. The registrar validates the credentials and records the Contact address — the IP:port from which the request arrived (after NAT traversal).

However, when the SIP server sends inbound traffic (INVITE for calls, NOTIFY for status updates) to a registered endpoint, it simply sends UDP packets to the stored Contact address. There is no authentication in the inbound direction — it's fire-and-forget UDP.

The Failure Chain

    ↓

    ↓

NAT Port Recycling on AKS

AKS nodes use SNAT (Source NAT) for outbound traffic. When a phone-worker pod sends a SIP REGISTER from inside the cluster, the AKS node translates the source address from the pod's internal IP (10.244.x.x:5060) to the node's external IP with an ephemeral source port (e.g. 40.88.229.41:1117). The SIP registrar records this NAT'd address as the Contact.

When the original stslakepine pod was evicted or rescheduled, its NAT mapping was released. A subsequent mapping reuse caused port 1117 on the same external IP to route into a different pod — Jefferson City's pod. The SIP registrar, still holding the stale Contact binding, continued sending stslakepine traffic to that address.

Why the mixing stopped after pod rollover

When pod td45p was replaced by zjglm, the new pod landed on a different node (aks-npapps-59438348-vmss000001) with a different external IP and different NAT port assignments. The stale 40.88.229.41:1117 mapping no longer routed to any active pod, so stslakepine traffic stopped arriving. Eventually the SIP registrar's binding will expire (typically 60–300 seconds after a missed re-REGISTER), and the traffic will stop entirely.

Why the Phone-Worker Accepted Foreign Traffic

The phone-worker application listens on UDP port 5060 and processes all incoming SIP messages — REGISTER responses, NOTIFYs, and INVITEs — without checking whether the Request-URI or To header matches the identity it registered with. This means any SIP traffic that reaches the pod's port 5060 will be accepted and processed, regardless of which SIP account it's addressed to.

Impact: Wrong Client Attribution

At least 3 real phone calls were processed through the wrong client identity. The INVITEs arrived via the stslakepine Contact address, but the phone-worker published MQTT messages using Jefferson City's client configuration. These calls would appear in Jefferson City's call log rather than the intended stslakepine client's log. Conversely, the stslakepine client's real calls were silently lost — they went to a pod that attributed them to someone else.

✔ Self-Resolution

The traffic mixing resolved itself at 13:57 UTC when a rolling update replaced pod td45p with zjglm on a different node. No manual intervention was required for the immediate symptom.

🔎 Unanswered Questions

Which client is stslakepine?

The SIP account sip101u_stslakepine belongs to a different Fetchit client whose phone-worker pod previously ran on the same AKS node. The stslakepine name needs to be mapped back to a client namespace to determine: (a) whether that client's pod is currently running and properly registered, and (b) whether they experienced missed calls during the mixing window.

Has this happened before?

SigNoz log retention only goes back to September 21, 2026. There is no evidence of mixing before October 1 in the available data, but the same NAT recycling mechanism could have caused similar incidents previously without detection. The phone-worker does not log a warning when it receives SIP messages for a foreign identity, so prior occurrences would only be visible by correlating SIP URIs across pod logs.

How many clients are potentially affected?

Any phone-worker pod using SIPProxy on the cluster is susceptible to receiving misdirected traffic when NAT port mappings are recycled. With 200+ phone-worker pods sharing a small number of AKS node external IPs, port reuse collisions are statistically inevitable over time.

📝 Lessons Learned

SIP Authentication Is One-Way — Inbound Traffic Is Unauthenticated

SIP REGISTER requests are authenticated with username/password, but the server's inbound INVITE and NOTIFY messages are sent to the stored Contact address over plain UDP with no authentication. Any process listening on the destination IP:port will receive and can process the traffic. Applications must validate that incoming SIP messages are addressed to their registered identity.

NAT Port Recycling Creates Cross-Client Contamination Risk

When 200+ phone-worker pods share a handful of AKS node external IPs, SNAT port mappings are a finite resource that gets recycled. A stale SIP binding pointing to a recycled NAT port can route one client's calls to a completely different client's pod. This is an inherent risk of running SIP over UDP behind shared NAT — and it's invisible without explicit identity validation in the application.

Pod Rollover Masked the Problem

The mixing resolved itself when the pod moved to a different node during a rolling update. This makes the issue transient and hard to reproduce — it only occurs when a specific combination of NAT port recycling and stale SIP bindings align. Without the SigNoz log investigation, this incident would have gone entirely unnoticed.
