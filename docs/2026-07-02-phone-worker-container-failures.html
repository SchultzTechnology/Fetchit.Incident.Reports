📊 Executive Summary

During the window 09:05:22 – 10:41:59 UTC on July 2, 2026, multiple phone-worker containers across different client namespaces were in active CrashLoopBackOff, with several pods accumulating hundreds of restarts. Simultaneously, the nginx ingress controller deployment was cycling new pods due to a pre-existing ImagePullBackOff caused by invalid Azure Marketplace ACR credentials, and the HPA could not scale the ingress controller due to missing CPU resource requests.

No OOMKills, node scheduling failures, or ERROR-level application logs were observed. The phone-worker crashes are application-level and their crash-time logs are not captured (pods die before emitting diagnostics). The ingress controller issues are infrastructure misconfigurations that predate this window.

Note — Silent Crash Logs

Pods with very high restart counts (especially brentwoodanimalhospital and blackcreekpetclinicatpoochies) produce no application logs during the incident window. This is consistent with a pod that is in deep exponential backoff — the container is crashing too quickly on startup to emit diagnostic output before Kubernetes delays the next restart. The root cause of the crash cannot be determined from logs alone; kubectl describe pod and previous container exit codes should be examined.

🐳 Issue 2 — Ingress Controller ImagePullBackOff

Pod ingress-controller-nginx-ingress-controller-6b84489bff-ck9kz in the default namespace has been permanently stuck in ImagePullBackOff for an extended period, accumulating over 149,720 retry events by the end of the incident window.

The image marketplace.azurecr.io/bitnami/nginx-ingress-controller:1.1.1-debian-10-r0 is an Azure Marketplace offering. The pull failure indicates one of:

  • The Azure Marketplace subscription for this image has lapsed or been deprovisioned
  • The cluster's managed identity / ACR pull credentials do not have access to the Marketplace registry
  • The image tag 1.1.1-debian-10-r0 has been removed from the registry

Two additional new ingress pods (grj8v at 09:24 and xhhrx at 09:54) came up during the window, indicating the deployment was rolling or scaling — and those new pods also immediately began failing HPA metric collection, confirming the configuration problem is in the deployment spec itself.

Impact Assessment

Other replicas of the ingress controller deployment appear to be serving traffic normally (SIP registrations and application calls were observed succeeding throughout the window). This specific pod is a dead replica but its continued BackOff loop generates noise and consumes Kubernetes event storage.

📈 Issue 3 — HPA FailedGetResourceMetric

The HorizontalPodAutoscaler targeting the nginx ingress controller deployment has been unable to collect CPU metrics since at least 2026-07-01 22:26:38 UTC, and continued generating failures throughout the incident window.

HPA Warning Events (recurring throughout window)
failed to get cpu utilization: missing request for cpu
  in container controller of Pod ingress-controller-nginx-ingress-controller-6b84489bff-*
HPA: ingress-controller-nginx-ingress-controller (autoscaling/v2)
Event count: 1,808 at 09:09 → 2,033 at 10:29

The root cause is that the controller container in the ingress deployment has no CPU resource request defined. Kubernetes requires a resource request to calculate utilization percentage for HPA. Without it, the HPA cannot make scaling decisions and will never scale the deployment up or down.

🔧 Actions Required

P1 — Investigate Phone Worker Crashes

Run kubectl describe pod <pod-name> -n <namespace> on the highest-restart pods (start with blackcreekpetclinicatpoochies and bestfriendsanimalhospital) to capture exit codes and last termination reason. Check kubectl logs --previous on any pod not in deep backoff to get the crash-time stack trace. The wide spread across unrelated client namespaces suggests a shared code path or external dependency (e.g. SIP registration server, config service, or secrets provider) is the failure point.

P2 — Fix Ingress Controller Image Pull

Resolve the pull failure for marketplace.azurecr.io/bitnami/nginx-ingress-controller:1.1.1-debian-10-r0. Either restore the Marketplace subscription / ACR pull permissions, or update the deployment to use a different registry (e.g. Docker Hub or a private ACR mirror). Once resolved, delete the stuck pod ck9kz to stop the BackOff noise.

P3 — Add CPU Resource Requests to Ingress Controller

Add a resources.requests.cpu value to the controller container spec in the ingress controller deployment. This unblocks the HPA and allows it to scale the deployment appropriately. Example: 

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
P4 — Improve Phone Worker Startup Logging

The most actionable improvement for debugging future crashes is ensuring the phone-worker logs its failure reason synchronously at process exit, before the container terminates. Crash-time diagnostics are currently unavailable because the pod exits before the OTel exporter can flush. Consider writing crash logs to stderr synchronously or using a Kubernetes preStop hook to flush telemetry.

✅ Fixes Applied

Issue 1 — Root Cause Identified & Documented

Status: INVESTIGATED (code-level fixes required)

Performed deep-dive analysis on highest-restart pods using kubectl describe and kubectl logs --previous to capture exit codes and crash signatures.

Findings:

  • Pod: blackcreekpetclinicatpoochies/phone-worker-bc97b48b-bnnkg (670 restarts)
    • Exit Code: 139 (segmentation fault)
    • Root Cause: NullReferenceException in SIPProxy plugin
    • Location: PhoneSystemsPlugins/SIPProxy/PhoneSystem.cs:line 80
    • Details: ServerCallCancelled event handler attempts .Contains() on cancelRequest.Header.Reason without null check before dereferencing
    • Fix Required: Add null guard: if (cancelRequest?.Header?.Reason?.Contains(...) ?? false)
  • Pod: bestfriendsanimalhospital/phone-worker-5b759d54b4-rpkz9 (451 restarts)
    • Exit Code: 1 (intentional exit)
    • Root Cause: Watchdog timer in CoreDial XMPP plugin
    • Location: PhoneSystemsPlugins/CoreDial/PhoneSystem.cs:lines 15–105
    • Details: Watchdog fires every 60 seconds, checks for XMPP message activity. After 3 minutes of silence, logs "No activity detected for over 3 minutes. Forcing application exit." and calls Environment.Exit(1)
    • Status: By design, but may warrant review of 3-minute timeout threshold

Impact: SIPProxy crash requires code patch and redeployment. CoreDial behavior is intentional but may indicate aggressive inactivity detection or configuration issue with XMPP server connectivity.
